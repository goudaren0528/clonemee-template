# 修复 `v0`

开发 Agent 用。输入：派发说明里指出的问题来源——审查报告 `reviews/P<n>-r<N>.md`、测试报告 `acceptance/report-r<N>.md`，或者跟进 Agent 的说明（比如合并冲突）。

## 步骤
1. 读问题来源，列出所有「范围内要修」的条目；「范围外观察」**不修**
2. 读进度文件 `packages/P<n>.md`（在需求分支上修集成测试的问题时，没有进度文件就在 `acceptance/` 对应报告旁边的修复记录里写）
3. 逐条修：
   - 先复现（按报告里的步骤或测试），确认问题存在
   - 找根因再改，最小改动，不顺手重构
   - 补一条能抓住这个问题的测试（单元或 e2e，能补就补）
   - 不同意某条：在终端里说明理由和证据，等跟进 Agent 定，不要自己跳过
4. 全部修完后跑一遍 dev-build 的自测（单元测试、构建、冒烟）
5. 在进度文件「修复记录」加一节：第 N 轮 · 来源 · 每条问题 → 改了什么 → 证据；提交
6. 在终端里说「修好了」，附每条的处理结果

## 合并冲突
跟进 Agent 让你「把需求分支（或 develop）合进当前分支并解决冲突」时，这是**唯一允许的合并**：
- `git merge <需求分支或 develop>`，逐个解决冲突：保留双方的意图，拿不准时以 PRD 和接口约定为准
- 解决后跑自测，提交合并结果，在终端里说清楚改了哪些冲突

## 禁止
- 修「范围外观察」、借修复做重构或加功能
- 改审查报告、测试报告、用例来让问题「消失」
- 推送；除上面那种情况外合并或切换分支
